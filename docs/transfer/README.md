# Перенос библиотеки в src-heating

Дата: 12 октября 2026, обновлено 19 октября 2026. Статус: пакет `0.4.2`
установлен в редактор, генераторы строят модели и грузят текстуры в его
воркере, порты работают; четыре рецепта узлов (`ASSEMBLY_RECIPES`) ставятся
в редакторе из каталога.

Цель — подключить библиотеку генераторов `src/lib` к редактору отопления
`C:\OpenServer\domains\skeleton-wf\src-heating`. Исходный план интеграции
находится в `skeleton-wf/docs/heating/heating-catalog-stand-plan.md`, разделы 5–8.

Библиотека поставляется отдельным пакетом. Стенд остаётся местом разработки и проверки
генераторов, а подключение к редактору начинается с небольшого проверяемого сценария.

## 1. Что уже готово

- `src/lib` не обращается к `window`, `document` и рендереру. Это проверяет
  `tsconfig.lib.json`, поэтому генераторы могут работать в воркере сцены `src-heating`.
- Внешний код подключает библиотеку через одну точку входа `src/lib/index.ts`.
- Версия `three` — `0.182.0` в обоих проектах. Из сторонних пакетов библиотеке нужен
  только `three`; `lil-gui` использует лишь стенд.
- Генератор возвращает модель как данные (`GeneratedModel`), а не как объект сцены.
  Объект сцены собирает `createModelObject(model, library)`.
- У генератора есть `version`, нужное для будущих миграций сохранённых проектов.
- Координаты библиотеки и редактора — в метрах.
- На 12 октября 2026 `npm run typecheck` проходит, `npm test` — 41 файл, 3198 тестов,
  все проходят.

## 2. Пакет библиотеки

Сделано 17 октября 2026. Исходники остаются в `src/lib`, стенд импортирует их
как раньше; пакет — результат сборки.

- `npm run build:lib` собирает `dist-lib/package` и архив
  `dist-lib/ingplan-heating-generators-<версия>.tgz`:
  - `index.js` — ESM, Vite в library mode (`vite.lib.config.ts`), без минификации,
    с картой исходников;
  - `types/` — декларации (`tsconfig.lib-types.json`, те же правила, что
    у `tsconfig.lib.json`);
  - `textures/` — PNG из `public/textures`;
  - `manifest.json` — версия пакета, версия three и список генераторов
    (ID и версия), снятый с собранного модуля;
  - `package.json` и `README.md` — из `lib-package/`.
- Имя пакета — `@ingplan/heating-generators`, версия — в `lib-package/package.json`
  (поднимать вручную при каждом выпуске). `private: true`: пакет не публикуется,
  а ставится архивом.
- Three.js в пакет не входит: `three` и `@types/three` — `peerDependencies`
  `~0.182.0`, а в `rolldownOptions.external` указаны `three` и все `three/...`.
- `exports` открывает только корень пакета, `textures/*` и `manifest.json`;
  внутренние модули закрыты.
- `npm run verify:lib` проверяет архив на чистой установке во временной папке:
  three не попал в модуль, каждый генератор строит модель по умолчаниям,
  а объект сцены собран из three потребителя; `manifest.json` совпадает с реестром;
  текстуры доступны по экспорту; декларации проходят `tsc` у потребителя;
  внутренний модуль не импортируется.

С `0.2.0` `verify:lib` проверяет пакет и в настоящем web worker (п. 3.4).
Не проверено: запуск из подкаталога сайта.

Копирование исходников в `src-heating` — только для разового эксперимента:
копии быстро расходятся.

## 3. Текстуры в воркере

Сделано 17 октября 2026 (пакет `0.2.0`). Текстуры грузит общий загрузчик
библиотеки `loadMaterialTextures(materials, resolveUrl)`
(`src/lib/materials/MaterialTextures.ts`): им пользуются и стенд, и редактор,
поэтому проверенное на стенде совпадает с тем, что видно в редакторе.

### 3.1. Доставка файлов

PNG из `public/textures` входят в пакет (`<пакет>/textures/*`); список файлов
по ключам — `MATERIAL_TEXTURE_FILES`. Адрес файла даёт потребитель через
`resolveUrl`: стенд — `BASE_URL + 'textures/'`, редактор — импорты
`'<пакет>/textures/x.png?url'`, Vite даёт файлу хеш и учитывает base
(маленькая резьба встраивается как data URL — fetch в воркере её читает).
Источники текстур — в README пакета.

### 3.2. Ориентация

Загрузчик работает через `ImageBitmapLoader` (fetch и createImageBitmap, без
Image и DOM — одинаково в главном потоке и в воркере). У `ImageBitmap`
`Texture.flipY` не действует, поэтому картинка переворачивается при
декодировании: `imageOrientation: 'flipY'`. Проверено сравнением кадров
на стенде: манометр, термоманометр и резьбовая муфта с пяти сторон —
с `TextureLoader` и с новым загрузчиком кадры совпадают попиксельно.

### 3.3. Владение и освобождение

`MaterialLibrary` владеет текстурами вместе с `ImageBitmap` под ними:
при замене текстуры и в `dispose()` вызывает `texture.dispose()`
и `ImageBitmap.close()`. Текстура, пришедшая после `dispose()` (загрузка
закончилась после закрытия сцены), сразу освобождается.

Отказ одной текстуры другие не отменяет: загрузчик возвращает список отказов,
материал остаётся без карты — резьба гладкая, циферблат белый. Стенд пишет
предупреждение в панель, редактор — в консоль.

### 3.4. Проверка в настоящем воркере

`npm run verify:lib` (`scripts/lib-worker-check.mjs`) запускает headless Chrome,
и module worker работает с архивом пакета без DOM: строит модели всех
генераторов, грузит текстуры загрузчиком и рисует манометр на `OffscreenCanvas`
с картой и без неё — на циферблате с картой должны быть тёмные деления шкалы.
Голые импорты (`three`, имя пакета) тестовый сервер переписывает на пути
в `node_modules`: import map в воркере не работает. Путь к Chrome —
`CHROME_PATH`, по умолчанию стандартная установка Windows.

Переводить стенд на воркер не нужно: генераторы проверяет `tsconfig.lib.json`
и эта проверка, а загрузку текстур — общий загрузчик.

## 4. Код в src-heating

Редактор к подключению готов, описание — в skeleton-wf:
`docs/heating/heating-catalog-objects.md` (устройство модуля) и
`docs/heating/catalog-integration-preparation.md` (чек-лист). На 17 октября 2026:

- **Контракт.** Модуль работает с генератором через свой интерфейс
  `HeatingGenerator` (`generators/HeatingGenerators.ts`): ID, версия, схема
  параметров, проверка, габарит. Сейчас за ним временные генераторы с теми же
  ID, версиями и схемами, что у библиотеки. Адаптер библиотеки встаёт сюда,
  модель сцены — в `view/HeatingModelFactory.ts` (сейчас коробка по габариту).
  Остальной модуль о библиотеке не знает.
- **Экземпляры.** Деталь — экземпляр позиции каталога: параметры задаются при
  установке и потом не правятся, меняются только этаж, положение и поворот.
  Перестроения по новым параметрам (бывший п. 4.2) нет.
- **Сохранение.** Формат проекта — версия 4: у каждого этажа секция `heating`
  с деталями (`id`, позиция каталога, `generatorId`, `generatorVersion`,
  полные `params`, положение, поворот). Неизвестная модель, другая версия
  генератора или негодные параметры отклоняют проект до правки сцены.
- **Протокол.** Команды вставки, правки положения, копирования и удаления;
  модели строятся в воркере, через сообщения ходят только данные.
- **Материалы.** Один `MaterialLibrary` на сцену; деталь освобождает только
  свою геометрию (`model.dispose()`), материалы и текстуры — владелец
  библиотеки при закрытии сцены.

Что осталось на стороне редактора: адаптер реестра и фабрики, загрузка
текстур в воркере (раздел 3), источник описаний каталога (подписи и категории
редактора поверх `CATALOG`), затем порты и сборки.

## 5. Проверки

В skeleton-wf нет vitest, а `tsconfig.heating.json` включает DOM. Поэтому тесты
и `tsconfig.lib.json` остаются на стенде, и новая версия пакета выпускается только после
успешных `npm run typecheck`, `npm test`, `npm run build:lib` и `npm run verify:lib`.

Интеграция проверяется на двух моделях:

1. **Простая муфта** — создание, изменение параметров, удаление, сохранение и повторная
   загрузка.
2. **Прибор с циферблатом** — загрузка ресурсов, ориентация текстуры и поведение
   при её отсутствии.

Затем проверяются переключение вкладок и этажей, освобождение памяти и проверки
из `skeleton-wf/docs/heating/heating-editor.md`.

## 6. Доработка после переноса

Стенд остаётся основным местом разработки каталога:

1. Новый генератор добавляется по разделу 7 [ARCHITECTURE.md](../ARCHITECTURE.md);
   общие тесты подхватывают его автоматически.
2. Проверка на стенде: `npm run typecheck`, `npm test`, просмотр в браузере.
3. Выпуск нового архива пакета и установка его в skeleton-wf.

Код редактора при этом менять не нужно: новые позиции появятся через
`GeneratorRegistry` и `CATALOG`.

Ограничения:

- **ID генератора** (`steel.coupling` и подобные) после появления сохранённых проектов
  не меняется.
- **Если изменились параметры или геометрия** выпущенной модели, нужно увеличить `version`
  и добавить миграцию старых параметров либо понятный отказ загрузки.
- Пока редактор — MVP, сохранённые проекты при обновлении пакета могут
  перестать открываться, и это допустимо. До появления пользователей правила
  совместимости уточняются (skeleton-wf, `catalog-integration-preparation.md`,
  раздел 11): версия растёт только при несовместимой смене параметров,
  генератор из реестра не удаляется.
