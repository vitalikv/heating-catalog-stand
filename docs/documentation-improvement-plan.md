# План улучшения документации

Дата: 9 октября 2026.

**Статус:** запланировано. Документ описывает будущие изменения; создание плана не означает их выполнения.

## 1. Цель

Разделить текущее устройство библиотеки, историю переноса и будущие задачи.
Разработчик должен находить актуальный контракт, рабочие инструкции и ограничения
без необходимости сопоставлять несколько завершённых планов.

Сохранить формулы, инвентаризацию `gl2`, снимки и причины осознанных расхождений.

## 2. Структура документов

| Документ | Назначение после изменений |
| --- | --- |
| `README.md` в корне | Запуск проекта и ссылки на документацию |
| `docs/README.md` — новый | Карта документов: что читать для использования, расширения и сверки библиотеки |
| `ARCHITECTURE.md` | Текущее устройство, контракт, ограничения и правила расширения |
| `library-usage.md` — новый | Пример подключения, обработка ошибок и освобождение ресурсов |
| `gl2-verification.md` — новый | Актуальная инструкция автоматической и визуальной сверки |
| `roadmap.md` — новый | Только незавершённые задачи, зависимости и критерии готовности |
| `gl2-differences.md` — новый | Журнал осознанных отличий от `gl2`, перенесённый без потери записей |
| Четыре существующих `*-plan.md` | История разработки, переноса, рефакторинга и интерфейса угла стыка |
| `documentation-improvement-plan.md` | Порядок выполнения этой работы |

При расхождениях между описанием текущего состояния и историческим планом
ориентир — `ARCHITECTURE.md`; при расхождении документации с реализацией нужно
проверить код и исправить описание либо отдельно зафиксировать дефект реализации.
Будущие решения не описывать как уже реализованные.

## 3. Порядок работ

### Шаг 1. Разделить текущую документацию и историю

- [ ] Создать `docs/README.md` с назначением документов и рекомендуемым порядком чтения.
- [ ] В четырёх завершённых планах добавить явную пометку: исторический документ,
  этап завершён, актуальные инструкции находятся по указанным ссылкам.
- [ ] Убрать утверждение о самодостаточности и главенстве `development-plan.md`.
- [ ] В `library-refactoring-plan.md` обозначить вводную часть и разделы с исходными
  проблемами как состояние **до** рефакторинга. Сохранить исходные решения и итоги шагов.
- [ ] В `joint-angle-ui-plan.md` обозначить требования как выполненную постановку задачи,
  включая отличие первоначального предложения хранить углы в `Map` от итогового `AssemblyJoint.angle`.
- [ ] Обновить навигацию в корневом README.

**Готовность:** из каждого исторического плана есть переход к актуальному описанию;
нет двух документов, одновременно объявляющих разные контракты действующими.

### Шаг 2. Вынести актуальную инструкцию сверки с `gl2`

- [ ] Создать `gl2-verification.md` на основе раздела 5 `catalog-porting-plan.md`,
  сверив команды и параметры с `scripts/gl2-compare.mjs` и `scripts/gl2-snapshot.mjs`.
- [ ] Описать зависимости: старый проект в OpenServer, сервер стенда, Chrome с CDP,
  требования к Node.js для скриптов. Отделить их от обычного запуска и тестов библиотеки.
- [ ] Привести команды запуска сверки и снимков, пример `cases.json`, расположение результатов.
- [ ] Заменить устаревший пример `new lib.<Класс>(new lib.MaterialLibrary()).build(cdm)`:
  текущий путь — перевод через `fromGl2`, получение генератора из `GeneratorRegistry`
  и построение по новым параметрам. Уточнить, что `legacy/gl2` используется внутренними
  инструментами сверки и не входит в обычный публичный API потребителя.
- [ ] Описать измеряемые величины, допуски и исключения, включая отсутствие эталона трубы.
- [ ] Отдельно описать обновление фикстуры: источник данных, основания для изменения,
  просмотр diff и запись причины. Не обновлять эталон только ради прохождения теста.
- [ ] Перенести журнал из раздела 12 `development-plan.md` в `gl2-differences.md`.
  Сохранить старый раздел как указатель, обновить ссылки на журнал.
- [ ] Перенаправить README и архитектуру на новую инструкцию. В старом разделе сверки
  оставить ссылку и исторический контекст вместо второй действующей инструкции.

**Готовность:** команды соответствуют текущим скриптам; пример не требует удалённых
экспортов; понятно, как выполнить сверку и оценить результат. Если среда `gl2` недоступна,
явно отметить, какие команды проверены только по коду, а какие реально запускались.

### Шаг 3. Уточнить добавление генераторов вне `gl2`

Исходное расхождение: раздел 7 `ARCHITECTURE.md` описывает добавление нового генератора,
но `tests/catalog.test.ts` требует полного равенства каталога наборам `gl2`, а
`tests/legacyGl2.test.ts` — полного равенства реестра целевым ID таблицы legacy.
Генератор без аналога в `gl2` нарушит эти проверки.

- [ ] В инструкции разделить перенос модели из `gl2` и создание самостоятельной модели.
- [ ] Явно описать действующее ограничение тестов и не обещать, что добавление
  самостоятельного генератора уже поддерживается всем набором проверок.
- [ ] В `roadmap.md` добавить отдельную задачу изменения тестов: проверять соответствие
  перенесённой части каталога, сохраняя общие проверки всех генераторов.
- [ ] Для этой задачи зафиксировать критерии: дополнительный генератор без legacy проходит;
  потеря перенесённого генератора или изменение его эталонных позиций обнаруживается.

**Готовность:** инструкция соответствует сегодняшней реализации; необходимое изменение
тестов оформлено отдельной задачей и не маскируется правкой текста.

### Шаг 4. Описать использование и владение ресурсами

- [ ] Создать `library-usage.md` с примером импорта из `src/lib/index.ts`, получения
  генератора, копирования `defaults`, проверки параметров, построения модели и объекта сцены.
- [ ] Показать обработку неизвестного ID и `GeneratorParamsError`.
- [ ] Показать удаление объекта из сцены и освобождение модели; отдельно — завершение
  работы общей библиотеки материалов.
- [ ] Зафиксировать владельцев: геометрия принадлежит модели, материалы и переданные
  текстуры — `MaterialLibrary`; `createModelObject` использует геометрию модели без копирования.
- [ ] Описать, что замена текстуры освобождает предыдущую, а несколько объектов,
  использующих одну модель, требуют согласованного момента `dispose()`.
- [ ] Указать, что автоматический подсчёт владельцев и кэш моделей не реализованы.

**Готовность:** пример проверен на текущем API, включая вложенные параметры и порядок
освобождения ресурсов. Для подключения библиотеки не требуется разбирать код стенда.

### Шаг 5. Уточнить границу воркера и ограничения сборок

- [ ] В `ARCHITECTURE.md` разделить выполнение генераторов без DOM и передачу результата
  между потоками. `GeneratedModel` содержит `BufferGeometry` и `dispose()`;
  готового транспортного формата и адаптера сериализации пока нет.
- [ ] Перечислить будущие данные передачи: атрибуты геометрии, группы материалов,
  ключи материалов, разъёмы, габариты, название и предупреждения. Пометить это как
  требования к будущему адаптеру, не как существующий API.
- [ ] Добавить описание `Assembly`: порядок деталей, требования к уникальности имён,
  ссылка `attach` на уже поставленную деталь и поведение деталей без `attach`.
- [ ] Разделить требования к входным данным и проверки, реально выполняемые кодом.
  Описать `errors`, диагностическое размещение несовместимых стыков и поведение
  при отсутствующем генераторе или разъёме.
- [ ] Описать единицы угла, действие `setAngle`, матрицы, габариты и освобождение сборки.
- [ ] Указать ограничения для замкнутых связей и использования сборки в редакторе:
  текущий механизм последовательного размещения не описывать как универсальный решатель связей.

**Готовность:** потребитель видит реализованные возможности и ограничения;
отсутствие DOM не выдаётся за готовую сериализацию, а диагностика сборки — за строгую валидацию.

### Шаг 7. Проверить согласованность

Для правок только Markdown запуск всей сборки и тестов не обязателен. Примеры TypeScript
нужно проверить компилятором в подходящем контексте проекта; команды сверки — запуском
при наличии нужной среды. Если работа потребует изменений кода, проверки определяются
отдельно по этим изменениям.

## 4. Приоритет и границы

Сначала выполнить шаги 1–3: устранить конфликт источников, устаревшие рабочие примеры
и неточность инструкции расширения. Затем шаги 4–6, в конце — общую проверку.

В этот план не входят изменения геометрии, публичного API, тестовых условий,
реализация воркера, миграций, кэша и интеграции с редактором. Обнаруженные необходимые
изменения реализации фиксируются отдельными задачами в `roadmap.md`.

Документы не переносить в другую папку без необходимости: исторический статус
можно обозначить на существующих путях, сохранив внешние ссылки.
